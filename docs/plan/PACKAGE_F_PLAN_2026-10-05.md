# GORGONA — пакет F: единая занятость ресурсов (CORE-04), план на согласование

Статус: **согласовано владельцем 2026-10-05** (ответы на четыре решения ниже:
служебная резервация как второй потребитель, вместимость > 1 позже,
`resource_blocks` отдельно, `booking_allocations` остается таблицей до конца
этапа 1). [ADR-0022](../adr/0022-shared-resource-occupancy.md) — Accepted. Основа — принятый E3
`b8834fb` (ветка `claude/package-e3-agreements`), мастер-план §12.2.1 и критерий
CORE-04.

## Контекст

- Занятость сейчас есть только у записи: `gba.booking_allocations` (миграция
  0003) с GiST-исключением `booking_allocations_no_overlap` для `HOLD`/`CONFIRMED`,
  статус записи переносится каскадом составного ключа, сервис берет
  `gba:resource:{tenant}:{resource}` в порядке id ресурса (ADR-0003). Перенос записи
  — отмена и новая вставка под теми же блокировками. Доступность читает
  `booking_allocations` и `gba.resource_blocks` (блоки персонала, вне исключения).
- Ресурсы: `artist`, `chair`, `room`, вместимость 1; запись одноресурсная
  (`booking_resources` limits: «no multi-resource booking … occupancy shared with
  other modules»).
- Тесты гонок: `api/tests/integration/test_booking_concurrency.py` (сырой SQL без
  блокировки, 100 попыток → 1 успех и 99 конфликтов, два экземпляра сервиса,
  истекшие удержания, подтверждение против новых удержаний, ключ идемпотентности).
- CORE-04: старый API записи и новая аренда одновременно запрашивают один ресурс —
  только один подтвержденный интервал; неудача откатывает все ресурсы. Пока
  переход не принят, новые модули не резервируют ресурс в отдельной таблице;
  двойная запись без единого механизма блокировки недопустима.

## Решения владельца, нужные до кода

1. **Второй реальный потребитель для CORE-04.** Вариант A (рекомендуется):
   минимальная служебная резервация ресурса (комната/оборудование/кресло на
   интервал, владелец — сотрудник компании, без клиента и оплаты) как первый
   источник `reservation`; модуль `assets` или отдельная строка реестра. Вариант
   B: ждать модуль аренды (этап 4) — тогда F закрывает переход записи, а CORE-04
   остается NOT TESTED. Тестовый «фиктивный» источник не предлагается.
2. **Вместимость > 1** сейчас (сумма под блокировкой, тесты) или вместе с первым
   потребителем, которому она нужна (рекомендуется второе).
3. **`resource_blocks`**: оставить отдельно (рекомендуется на этом шаге) или
   перенести как источник `block`.
4. **Форма переключения чтения**: `booking_allocations` остается таблицей,
   которую пишет общий путь, до закрытия этапа 1 (рекомендуется — проще откат),
   или заменяется совместимым представлением.

## Шаги (каждый: red→green, focused и полные проверки, независимый обзор, коммит, push, CI точного SHA, коммит приемки)

**F0 — характеризация (без схемы).** Зафиксировать текущее поведение тестами,
которые должны пережить переход: снимок ответов `/v1/salons` и `/v1/businesses`
по записи, доступности, переносу, отмене, истечению удержаний; эталон гонок.

**F1 — расширение (миграция 0018).** `gba.resource_allocations`: tenant, id,
resource_id, `source_kind` (закрытый список: `booking`, затем по решению 1),
`source_id`, `during` (полуоткрытый, ограниченный, непустой), `state`
(`held`/`confirmed`/`released`), `units` = 1, created_by/created_at.
FORCE RLS, restrictive-политики филиала (ресурс филиала), guard (+определения),
маркер 18, вставки и смена состояния только через функцию; исключение по
`(tenant_id, resource_id, during)` для активных состояний. Пока без записи из
кода — только схема и проверки.

**F2 — перенос и сверка.** Миграция копирует активные интервалы
`HOLD`/`CONFIRMED` из `booking_allocations` (идемпотентно, по ключу источника);
функция сверки (количество, владельцы, интервалы, состояния) и тест «до/после»;
на расхождении миграция падает. Отдельная проверка на копии данных, без
промышленной миграции.

**F3 — единый механизм.** SQL-точка входа и `occupancy.reserve/release/confirm`
в Python: блокировки ресурсов в стабильном порядке, все интервалы операции или
ни одного, 23P01 → один типизированный конфликт. Движок записи пишет через нее
(в той же транзакции обновляется совместимая `booking_allocations`; статус
записи по-прежнему атомарно меняет состояние занятости). Гонки: существующие
тесты + сырой SQL против обеих таблиц + многоресурсная операция с откатом.

**F4 — второй потребитель (по решению 1) и CORE-04.** Минимальный источник
`reservation` (API, права owner/manager и филиала по ADR-0014, аудит, gate
модуля, UI в рабочем месте). Тест CORE-04: запись через старый API и резервация
одновременно на один ресурс → один подтвержденный интервал; многоресурсная
неудача откатывает все.

**F5 — переключение чтения и откат.** Доступность, сводки и календарь читают
`resource_allocations`; `booking_allocations` остается совместимой формой;
документированный и проверенный откат чтения. Обновить limits `booking_resources`.
