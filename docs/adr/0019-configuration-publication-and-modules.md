# ADR-0019 — Configuration publication, module registry and readiness records

Status: accepted by the owner on 2026-10-04 for the stage-1 implementation increment (package D, CORE-02). Technically verified on `5320c4a` with full CI; see the [acceptance record](../plan/evidence/2026-10-04-configuration/ACCEPTANCE.md).

## Context

The master plan (§4 "Версии конфигурации и доступность модулей", §14.3) requires a company configuration with the states draft → validated → published → superseded, the author, version, validation result and previous published version kept; an immutable published version; expected-revision saves and idempotent commands. Industry selection must not enable unprepared operations; the server checks allowed modules and their dependencies; disabling a module stops new operations while history, open obligations and export stay available; a new mandatory module never switches on silently. Readiness of each profile and scenario is a separate record with five statuses; only confirmed capabilities are offered.

Today the profile draft (migration 0008, [CORE-02 for drafts](../plan/GORGONA_PLAN_AUDIT_2026-10-04.md)) stores industries and business formats as immutable revisions with `state = draft` only. There is no module concept, no publication and no readiness record apart from the `workflow_readiness` field of the industry catalog, which is always `planned`.

Owner decisions for this increment: businesses without a published configuration keep today's behaviour (an implicit baseline with booking enabled; the migration creates nothing on their behalf); disabling booking stops new bookings and reschedules, while cancellations, existing holds, history and reads continue; approval of the package plan authorizes implementation; each step is committed and pushed to the working branch without merge or deployment.

## Decision

- **Module registry in code.** `business/modules.py` (registry version 1) lists the 18 platform modules of §4 with stable ids, kind (`core` or `optional`), dependencies, readiness, limits and what stops when the module is disabled. `organization` and `users_access` are core and always enabled. `booking_resources` is the only optional module that can be enabled (technically verified; it carries its own service catalog). The other 15 modules are `planned` and cannot be enabled. A module can be enabled only if it is optional, at least `technically_verified` and its dependencies are enabled. Registry changes never alter a published configuration.
- **Readiness registry in code.** `business/readiness_registry.py` holds the five statuses, one record per scenario of §14.1.1 (28 ids: status, verified scope and limits, implementation and industry-acceptance owners left empty until assigned, code/schema/settings versions, evidence paths, date) and one full-workflow record per industry profile (39, all `planned`). The industry catalog derives `workflow_readiness` from it; catalog contract version 1 is unchanged. Statuses follow the audit and change only in a commit that cites evidence.
- **Configuration versions.** Migration 0014 adds `business_configuration_versions` (state, row revision, pinned profile revision, registry version, author and time of creation, validation, publication and supersession) and `business_configuration_modules` (the enabled optional modules of a version, attachable only in the creating transaction). A trigger keeps content immutable, forbids deletion, advances the row revision by one, and allows only draft → validated → published → superseded, each decision written once; only the latest version may be validated or published, and a published version is superseded only by the publication of a newer one in the same transaction. A partial unique index allows one published version per business.
- **Effective module state.** `business_module_states` keeps one row per optional module once a business has published: enabled or not, and the published version it came from (the trigger requires that version to be published). It is readable by every session of the business, including branch-limited ones, because booking enforcement and the workspace need it; version history stays company-wide only.
- **Enforcement at the database.** A `BEFORE INSERT` trigger on `gba.bookings` takes a shared advisory lock on `gba:business-configuration:{business}` and refuses the row with SQLSTATE `GBM01` when `booking_resources` is disabled. Publication holds the same lock exclusively, so a booking is ordered entirely before or after a publication. The trigger covers the management workspace, reschedule, the customer site, delegated employees and development holds through one place; `insert_booking` maps the error to 409 `MODULE_DISABLED`. Updates of existing bookings (cancel, confirm an existing hold) are not affected. The customer availability and hold routes also answer 409 `MODULE_DISABLED` before doing work.
- **Access boundary.** Both version tables get the company-only restrictive scope policy; `business_module_states` gets restrictive insert and update policies for company-wide sessions. The schema guard learns command-specific expectations (`USING` and `WITH CHECK` separately) and checks the booking trigger and its function; the runtime requires 29 approved policy definitions plus the trigger. Damaged definitions fail readiness.
- **API** under `/v1/businesses/{id}`: `module-catalog` and `readiness-registry` (`business.read`); `configuration` (published or baseline, latest version, effective modules), `configuration/versions` with paging and `…/versions/{v}`, `…/versions/{v}/preview` (difference from the effective configuration: modules enabled and disabled, operations that stop, industry changes, readiness limits, current problems and warnings) — all `business.read`. Commands need `business.manage`, company-wide access and an `Idempotency-Key`, are never delegable and are audited atomically: `PUT configuration/draft` (`expected_version`, `profile_revision`, `module_ids`), `POST …/versions/{v}/validate` and `POST …/versions/{v}/publish` (`expected_revision`). Validation failure answers 422 `CONFIGURATION_INVALID` with the problems and changes nothing; publication re-validates under the lock. A newer profile revision than the pinned one is a warning, not an error. `/v1/salons/{id}/workspace` gains `booking_enabled`.
- **Web.** A "Configuration" panel in Business profile shows modules with readiness and limits (planned modules cannot be selected), saves a draft pinned to the current profile revision, validates, previews and publishes after confirmation, lists history, and retries an uncertain result with the same key. Booking screens hide creation and reschedule and explain why when booking is disabled; cancellation and history remain.

## Acceptance

1. Draft → validate → publish → supersede keeps every version, author, result and predecessor; replays return the stored result; a reused key with another body is refused.
2. CORE-02: two concurrent saves of the same version give one success and one conflict; two publications give one success; stale revisions are refused.
3. Planned modules, missing dependencies, a changed registry and unknown references are refused with explanations.
4. With booking disabled, the management workspace, reschedule, customer site and a delegate cannot create bookings (409); cancellation and reads work; re-enabling restores creation; a publication racing a booking leaves no booking created after the disabling commit.
5. Direct SQL cannot change content, forge transitions, publish an older version, keep two published versions, delete history or toggle module states without a published version; damaged scope policies or a dropped booking trigger fail readiness.
6. Tenant isolation, branch-limited and read-only roles, platform support read-only access.
7. Real browsers: the owner sees module readiness, disables booking, validates, previews, publishes after a lost response with the same key, sees booking creation disabled while history remains, re-enables it in a new version; mobile accessibility and width; SQL confirms versions, states and audit.

## Consequences

The runtime requires migration 0014. Booking enforcement depends on a database trigger, so restoring an older application keeps the gate; removing the trigger is detected by readiness. Known limits recorded by review: the customer `bootstrap` response does not yet say that online booking is off (a visitor learns it at availability, 409); the schema guard compares the trigger function source on each branch-limited request, like the other access definitions, which adds a small catalog query. Out of scope and left for later increments: custom fields and process configuration from allowed actions (the rest of §4), enabling planned modules, configuration rights for groups or delegates, and moving the older stage-1 command helpers to the new shared helper `business/commands.py`.
