## Conformance and required changes

1. **Reuse the proposed child module.** `finance_documents`, depending on finance/counterparties, is a valid stable ID under current contracts. Keep finance/FIN-01 verified and derive the child readiness from the existing FIN-03 record, rather than maintaining a second acceptance flag. Its scope must cover the full H, including obligations/settlements/corrections, not only H1 invoice CRUD. Existing baseline and published finance-only configurations omit the child and remain OFF for H; a new owner/manager publication is required to opt in. Current backend/SQL module IDs and Zod catalog are generic, so no new configuration table or wire schema is needed.
2. **Bump module registry version 1→2 when adding the child.** The catalog changes from 18 to 19 entries. `configurations._problems` compares the draft's registry version with the current one, and publication revalidates; preserve published v1 configurations and immutable history. Stale v1 drafts must return REGISTRY_CHANGED and require a new draft. Update count/version snapshots, including the existing test that hardcodes2 as a mismatched version. When acceptance changes enableability again, advance the registry version accordingly. Catalog/configuration schema_version1 remains compatible; READINESS_REGISTRY_VERSION is a separate protocol value, not the configuration pin.
3. **Concrete incompatibility: do not gate every H insert unconditionally.** ADR-0024/plan H-09 retain recovery and safe non-money release while finance is OFF. A blanket `require_enabled_module('finance_documents')` + finance trigger on settlement/release/recovery tables would refuse those inserts. Follow G's ungated cancellation-control pattern; gate new monetary/source/reserve effects, while an explicit finite domain event guard permits only safe release/recovery without the enabled modules. Sent/unknown outcomes still require resolution, and the exception must never admit confirmation, credit, correction or a new reserve. A conditional event guard must be explicitly checked against its packaged source, not hidden behind an unchecked WHEN bypass.
4. **Keep G gates intact; extend H coverage precisely.** `schema_guard._MODULE_TRIGGERS` already supports multiple module gates on one table. Add both H/finance gate definitions and company-only/tenant policy expectations for the actual H tables. Preserve exact function/trigger/argument inspection and extra-permissive-policy rejection. H-owned invoice/credit/payment journal sources also need child gate + immutable H lineage in SQL; merely gating H tables must not permit direct H-source insertion into G while the child is OFF. Do not add the child gate to ordinary G manual/opening/reversal journals. Use forward0021 and approved source-specific/domain controls.
5. **Clarify publication readiness versus immediate runtime withdrawal.** Current `require_module` and `gba.require_enabled_module()` check the published enabled state; neither reads current Readiness. This is compatible with preventing first H activation through the real publisher. If the contract also requires an already-enabled H to stop immediately after readiness is withdrawn, H API mutations must check the current child readiness from that same registry record in addition to published selection. This needs no second flag. A catalog status alone does not alter SQL module state.
6. **Reuse the real fixture helper.** The existing helper is `verified_modules(...)` in tests/integration/module_support.py, using a scoped MonkeyPatch context. It patches MODULES_BY_ID plus the API-imported catalog, so real draft/validate/publish still runs. Override only the child in development fixtures and publish finance/counterparties/finance_documents together. Do not assume MODULES or the readiness-registry endpoint was also promoted by this helper. Keep a negative publication test against the unmodified registry; final H acceptance must use ordinary production readiness/publication without a positive override.
