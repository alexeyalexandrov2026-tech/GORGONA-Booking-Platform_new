## Smallest sound persistence slice

- Forward0021 only: document identity, immutable version snapshots/lines, an immutable invoice-origin obligation, and once-only operation→G journal linkage. Keep the existing counterparty-version and ledger-book/account/currency references. Every composite relationship includes tenant/book; party revision is pinned. Drafts append consecutive revisions; issue appends a complete copy of the current draft with actual issue references, never mutates it. No further draft/line mutation after issue. Positive bounded minor units and declared totals/line counts are SQL-validated, not merely request validators.
- Issue owns one READ COMMITTED transaction under the existing tenant ledger lock before membership share: authorization/gates → command claim/cancellation check → issued snapshot/lines → obligation and typed G append/link → complete coupled integrity checks → audit/reference receipt. Order cyclic inserts using only the necessary deferred FKs; generate IDs before inserts. Rollback at any step leaves no money effect or completed receipt.
- Add a small typed G append primitive inside the caller transaction, returning actual references. Reuse its account/currency/open-period/amount/source validations and SQL balance checks. Do not call the existing whole G `post_entry` command wrapper as an invoice operation: it owns a separate G idempotency receipt and serializes a v1 journal. The H command owns its single receipt and flushes H lineage plus G balance after the whole graph exists.

## Concrete bypass risks and required controls

| Risk | Required defense/check |
|---|---|
| A balanced journal with wrong amount, accounts, source or no real invoice | Deferred whole-document matching: exactly one issued version, invoice obligation and journal effect; principal/currency/book/direction/control account/source identity/issue metadata agree. Compare the complete expected control+counter-line multiset, including duplicates and multiplicity (EXCEPT ALL in both directions or equivalent), not just debit=credit or aggregate totals. A draft has no issued effects. |
| Early SET CONSTRAINTS consumes a header-only check, then a balanced late G debit/credit pair changes the effect | Requeue lineage validation on journal_lines as well as journal headers, versions, invoice lines, document anchors, obligations and operation links. Late inserts must recheck completed final state. G's existing two balance triggers stay intact but cannot prove invoice lineage. |
| Same transaction creates draft1→issue2, validates, then appends a draft1 line | Either reject adding older draft lines once the document is issued, or have every affected line trigger revalidate the final issued copy for the whole document. A trigger that checks only the triggering draft is insufficient. Use server-owned created_transaction markers to prevent later-transaction line/link additions; a timestamp/history marker alone does not seal later writes within the same transaction. |
| Direct SQL inserts an invoice-origin G journal or generic G reversal without H ownership | Source-specific SQL gates plus deferred bijective lineage enforce this independently of API. H1 permits only implemented invoice issue origin; future payment/credit origins remain closed. Deny generic reversal of an H-owned entry until a real H correction path exists. Do not attach the child gate to ordinary G manual/opening/reversal entries. |
| Guard drift, permissive-policy OR bypass, or replacing a G function while still expecting its0020 body | Retain old migrations/checksums. Prefer additive H functions/triggers so existing exact G-body approval remains valid. If a G function must change forward, explicitly approve its final packaged definition. Cover every new table's FORCE RLS/company scope/tenant policy and reject extra permissive policies; guard all lineage/history/module trigger definitions and arguments from trusted packaged SQL, never live-DB-derived expectations. |

[PostgreSQL18 SET CONSTRAINTS](https://www.postgresql.org/docs/18/sql-set-constraints.html) confirms that early IMMEDIATE checks pending changes and also controls constraint-trigger firing. Subsequent relevant inserts therefore need their own queued validation. [CREATE TRIGGER](https://www.postgresql.org/docs/18/sql-createtrigger.html) confirms alphabetical same-kind trigger ordering: declaration order is not an ordering guarantee.

## Compatibility, gate and recovery seams

- Preserve G-v1 manual/opening writes and old records. Introduce explicit extended journal-v2 read models/negotiation; keep the v1 source enum closed. Inspect raw source/ownership before constructing a v1 model: existing `load_entry` builds a v1 model before `reverse_entry` checks it, so a naive invoice-origin extension would produce a validation error instead of an intentional upgrade/refusal. Legacy detail/list reads must return a typed upgrade requirement, never filter out H origins or relabel them manual. Trial balance continues to include every G line.
- finance_documents remains unavailable according to current FIN-03 readiness and requires its own published selection plus finance/counterparties dependencies. Existing finance-only/v1 configurations never enable H. API checks current child readiness and published selection; SQL checks the published gates/source ownership. Development positive fixtures must remain active for the H test operations when testing this closed slice; final H acceptance removes them. Reads/recovery/cancellation remain available OFF; later non-money release exceptions need explicit domain-state validation, not a blanket ungated financial event table.
- Reuse FinancialCommandReference/FinancialReceipt and shared command/audit helpers for the finite invoice_draft/invoice_issue operations; preserve the six existing G commands unchanged. Permanent domain result metadata must bind operation/actor/key and book/document/revision sufficiently to distinguish a committed intended operation from another writer's winning version after ordinary receipt expiry. No body/amount/title/token in browser recovery. Resolve receipt first, then immutable domain evidence; safe cancellation under the same lock seals a late original before its claim. Cancellation records have no money effect and no finance_documents insert gate.
